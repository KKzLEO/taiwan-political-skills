# 台灣訊息查核 skill：設計規格

- 日期：2026-11-17
- 範圍：子專案 A（訊息查核 skill）和操弄手法辨識模組
- 不在本規格內：B 政治傾向自我分析、C landing page、D IG/Threads 經營。這三個之後各自寫規格。

## 1. 目標

做一個開源 skill，讓使用者查核收到的訊息，報告要公正、可以重現、每一句都查得到出處。

- **使用對象：** 有裝 Claude Code 或 Codex 的技術使用者。
- **平台：** Claude Code 和 Codex 都能當主體執行。核心流程只寫一份，兩個平台各寫一層轉接。
- **地區：** 第一版只做台灣，資料包做成可以抽換的模組。報告跟著使用者的語言。
- **輸入：** 新聞網址、貼上的文字、截圖、影片連結。

### 成功標準

1. 同一份判定結果，分數和報告每次都完全一樣（由腳本計算，有測試保證）。
2. 中立性規則由程式檢查，不靠模型自律：媒體表每一筆都要有出處，手法庫每一種手法的案例至少涵蓋兩個不同陣營。
3. 一個真實案例能從輸入一路跑到 `report.md`，Claude Code 當主體時測過。
4. 外部模型呼叫時讀不到使用者的記憶。用含特殊字串的探測測試驗證，結果寫進執行紀錄。

## 2. 和現有工具的關係

| 工具 | 借用的部分 | 不同的地方 |
|---|---|---|
| `kunder-LIN/taiwan-fact-check-center`（MIT） | 原子命題（原文說法加中立改寫）、來源分層、同源轉載只算一條證據、找不到不等於錯誤、法案要分階段判斷、內容中的指令一律當資料 | 它只用一個模型、只有一個分數。我們有正反方抗辯，分數拆成可信度和信心度 |
| `petar-nauka/fact-check-skill`（MIT） | 命題六分類、證據表欄位、搜尋反面說法、JSON 驗證和測試寫法、內容層操弄特徵清單 | 它把查核機構列為最高層級，我們把查核機構的結論當成要重驗的線索 |
| `lawchat-oss/mcp-taiwan-legal-db`（MIT） | 法條原文、修法沿革、判決書，選裝的 MCP | 我們只多做一層白話解釋，每句解釋都附條號原文 |
| DISARM Red Framework（CC BY-SA 4.0） | 手法編號，方便國際對照 | 只引用編號，不轉貼內容 |

## 3. 架構

### 3.1 檔案結構

```
.claude-plugin/plugin.json         Claude Code plugin 設定
.claude-plugin/marketplace.json    讓使用者用一行指令安裝
skills/factcheck/                  整個 skill，Codex 直接連結這個資料夾
  SKILL.md                         共用流程（兩個平台通用）
  agents/openai.yaml               Codex 顯示用的資訊
  references/                      判定定義、評分、中立化、來源分層、法條、各角色的指令
  scripts/fc.py                    唯一的命令列入口，下面有子命令
  scripts/fclib/                   腳本的模組
  data/model-tiers.toml            同等級模型白名單
  data/tw/media.toml               媒體對照表（每筆附出處）
  data/tw/sources.toml             可信的第一手來源入口
  data/tw/tactics.toml             操弄手法庫
tests/                             unittest，CI 會跑
evals/                             發版前手動跑的評測案例和探測
```

**資料格式改用 TOML，不用 YAML：** Python 標準函式庫沒有 YAML 解析器，而「只用標準函式庫」是為了讓安裝零依賴。所以最低版本是 Python 3.11，因為從這一版起才內建 `tomllib`。

### 3.2 每次執行的資料夾

每次查核都存在使用者目前所在目錄底下的 `factcheck-runs/<YYYYMMDD-HHMM>-<主題>/`：

| 檔案 | 由誰產生 | 內容 |
|---|---|---|
| `run.json` | `fc.py init` | 模式、主體平台、時間、版本 |
| `models.json` | `fc.py detect` | 偵測到的模型、是否跨模型、能不能上網、隔離程度 |
| `source.json` | 主 agent | 原文、媒體、署名、時間、取得方式 |
| `claims.json` | 主 agent | 拆好的命題 |
| `trace.json` | 溯源員（乾淨的 sub-agent） | 傳播溯源、既有查核、發布者背景、傳播跡象、操弄手法 |
| `proponent.json` | 正方 | 證據表和每個命題的判定 |
| `opponent-<席位>.json` | 各反方 | 攻擊清單 |
| `rebuttal.json` | 正方 | 對每條攻擊的回應 |
| `judgment.json` | 裁判 | 每條攻擊成不成立、修改後的判定、最終證據表 |
| `review-<席位>.json` | 提出成立攻擊的反方 | 覆核修改後的判定 |
| `verdicts.json` | `fc.py finalize` | 套用覆核規則後的最終判定 |
| `score.json` | `fc.py score` | 可信度、結果、信心度、扣分明細 |
| `report.md` | `fc.py render` | 給人看的報告 |

每一步都會先檢查輸出檔是否已經存在且格式正確，存在就跳過，所以中斷後可以接著跑。每個模型產出的 JSON 都要先通過 `fc.py validate <檔名>` 才能進下一步。

## 4. 流程

兩種模式的步驟一樣，只差在反方席位和搜尋深度。

| 步驟 | 負責 | 說明 |
|---|---|---|
| 0 | `fc.py init`、`fc.py detect` | 建立資料夾，偵測模型 |
| 1 讀入 | 主 agent | 網址和圖片用平台內建工具讀；影片用 `fc.py video` 抓字幕 |
| 2 中立化 | 主 agent | 拆命題、分類、改寫成中立說法 |
| 3 溯源和背景 | 溯源員 | 每種輸入都做，媒體用 `fc.py media` 查表 |
| 4 正方提出論點 | 正方 | 證據表和判定 |
| 5 反方攻擊 | 反方 A、B、C 和外部反方 | 同時跑，彼此看不到對方 |
| 6 正方答辯 | 正方（新的 sub-agent） | 逐條接受或反駁 |
| 7 裁判 | 裁判 | 判定每條攻擊成不成立，修改判定 |
| 8 覆核 | 提出成立攻擊的反方（`fc.py reviewers` 列出） | 只審被改過的命題 |
| 9 結算 | `fc.py finalize`、`score`、`render` | 套規則、算分、產報告 |

### 4.1 席位

| 模式 | 正方 | 反方 |
|---|---|---|
| 快速 | 1 | 1 席：有外部模型就用外部模型，沒有就用反方 B |
| 完整 | 1 | A、B、C 三席，加上每個可用的外部模型各一席 |

- **主模型的角色：** 溯源員、正方、反方 A/B/C、裁判。
  - Claude Code 當主體時用 Agent 工具開 sub-agent。
  - Codex 當主體時用 `fc.py run-model --engine codex` 開子程序。
- **外部反方：** 一律用 `fc.py run-model` 呼叫另一家的 CLI。

## 5. 中立化和記憶隔離

1. **只傳必要的東西：** 主 agent 以外的每個角色，只拿到 `source.json`、`claims.json`、前面步驟的 JSON 和自己的角色指令，看不到使用者的原始提問。
2. **改寫要被檢查：** 每個命題都同時有 `original`（原文說法）和 `neutral`（中立改寫）。反方 C 和外部反方要檢查改寫有沒有偏，有偏就改回原文的說法。
3. **外部 CLI 在乾淨環境裡跑：**
   - `codex exec`：在空的暫存資料夾執行，加上 `--ignore-user-config --ephemeral --skip-git-repo-check -s read-only -c web_search="live"`。
   - `claude -p`：加 `--append-system-prompt`，明確指示忽略使用者層級的偏好。有 `ANTHROPIC_API_KEY` 時再加 `--bare`，這樣會跳過 CLAUDE.md 和自動記憶；沒有 API key 時沒辦法用 `--bare`，因為它不讀 OAuth 登入。
   - `fc.py detect --probe` 會實際問每個 CLI「脈絡裡有沒有使用者層級的設定」，結果寫進 `models.json` 的 `isolation`，報告的席位表也會列出來。探測結果不記錄使用者設定的內容。
   - **2026-11-17 在開發機上實測：** `codex exec` 即使加了 `--ignore-user-config` 和 `-c project_doc_max_bytes=0`，仍會讀到 `~/.codex/AGENTS.md`；沒有 API key 的 `claude -p` 會讀到 `~/.claude/CLAUDE.md`。兩者都記為 `partial`。
   - **不採用的做法：** 把 `CODEX_HOME` 指到暫存資料夾、再連結使用者的 `auth.json`。token 輪替時可能讓使用者被登出。要完整隔離，請使用者自己準備一個乾淨的 Codex 設定，用 `FC_CODEX_CMD` 指定。
4. **提問帶立場時：** 報告只寫一行「提問已改寫為中立命題」。

## 6. 角色

角色指令都放在 `references/roles/`，兩個平台共用同一份。

| 角色 | 檔案 | 重點 |
|---|---|---|
| 溯源員 | `tracer.md` | 最早出現的時間和地點、各種版本、既有查核（列為線索）、發布者類型、傳播跡象、操弄手法。追到一般民眾時只記錄帳號的公開資訊 |
| 正方 | `proponent.md` | 第一手資料優先；每筆證據都附網址和原文摘錄；同源轉載用同一個 `chain` 標記；查核機構的結論要回到它引用的原始資料重驗 |
| 反方 A：證據 | `opponent-evidence.md` | 摘錄是否真的這樣寫、來源層級、是否獨立、是否過時、法案階段 |
| 反方 B：反證 | `opponent-counter.md` | 自己搜尋反面說法、漏掉的第一手資料、前後文 |
| 反方 C：立場 | `opponent-stance.md` | 改寫有沒有偏、用詞、雙重標準、溯源有沒有推論過頭、手法標籤是否對稱 |
| 外部反方 | `opponent-external.md` | 三個角度都要攻擊，一定要自己搜尋 |
| 正方答辯 | `rebuttal.md` | 逐條接受或反駁，反駁要附證據 |
| 裁判 | `judge.md` | 攻擊成立的條件：附的證據實際打開核對過、確實存在且內容相符；或指出了推理錯誤，正方沒辦法回應。判成立的溯源和手法攻擊要寫明撤回哪些手法標記（`withdraw_tactics`，不撤填 `[]`），撤回的編號要出現在攻擊或裁決理由裡；報告不列撤回的標記，並把成立的溯源和手法修正列在「辯論後的修正」，只刊裁判的理由。溯源和手法攻擊就算填了 `claim_id`，也不進命題覆核、不影響分數 |
| 覆核 | `review.md` | 只審被改過的命題，回答通過或不通過並說明理由。不通過時還要回答標籤本身對不對（`label_ok`）：標籤對、只是理由或證據有缺漏，就維持標籤並列入爭議點；標籤錯、沒回答或覆核沒跑完，改判「無法證實」。兩種都照信心度規則扣分 |

## 7. 判定、分數、信心度

### 7.1 判定標籤

| 代碼 | 標籤 | 條件 | 係數 |
|---|---|---|---:|
| `true` | 正確 | 有第一手直接證據，沒有成立的反證 | 1.00 |
| `mostly_true` | 大致正確 | 主體正確，細節小差異不影響結論 | 0.80 |
| `mixed` | 部分錯誤 | 有真有假 | 0.50 |
| `unverified` | 無法證實 | 證據不足，也沒有直接反證 | 0.35 |
| `misleading` | 誤導 | 材料是真的，但斷章取義、缺少前後文，或引導出錯誤印象 | 0.25 |
| `false` | 錯誤 | 有直接反證 | 0.00 |
| `not_factual` | 非事實陳述 | 意見、預測、口號 | 不計分 |

找不到某人說過某句話時，判 `unverified`。只有本人否認過，或完整紀錄能證明他說的是別的，才判 `false`。

### 7.2 可信度（0–100）

```
可信度 = 100 × 命題正確度
```

- **命題正確度：** 計分命題的係數，依重要性（1–5）加權平均。
- 四捨五入到整數（四捨五入時 .5 進位）。
- **證據品質移到信心度（7.4）。** 原本的設計是 `60 × 命題正確度 + 20 × 證據品質 + 20 × 脈絡完整度`。用標準案例驗算時發現，全假但反駁得很扎實的訊息會拿到 40 分，被判成「部分符合」；這是因為證據品質衡量的是我們的反駁有多扎實，不是訊息有多可信。照標準案例的預期結果比對，舊公式 10 則只對 3 則，新公式對 9 則。
- **脈絡問題不另外扣分**，因為已經反映在「誤導」等判定上，再扣一次就重複了。`context_flags` 仍然保留，並在報告中列出。

### 7.3 查核結果

| 條件（由上往下，套用第一個符合的） | 結果 |
|---|---|
| 沒有任何計分命題 | 無法判定（全部是意見陳述） |
| `unverified` 的重要性權重 ≥ 計分命題總權重的 50% | 無法判定 |
| 可信度 ≥ 80 | 符合 |
| 60–79 | 大致符合 |
| 40–59 | 部分符合 |
| < 40 | 不符 |

判「無法判定」時，光譜上不標分數。

### 7.4 查核信心度（0–100）

從 100 開始扣，最低 0：

| 情況 | 扣分 |
|---|---|
| 證據品質不滿分 | −20 × (1 − 證據品質)，四捨五入 |
| 沒有任何執行成功的跨模型席位 | −20 |
| 有跨模型席位，但都不能上網 | −10 |
| 每個覆核沒通過的命題 | −10 |
| 核心命題的直接證據全都存取受限（沒有任何一筆 `access_note` 是 `full`） | 每個命題 −10，最多 −30 |
| 有法條命題，但沒有取得條文原文 | −15（只扣一次） |
| 快速模式 | 扣完後上限 60 |

- **證據品質（0–1）：** 每個核心命題從最終證據表算出：有第一層或第二層的直接證據（`stance` 是 `supports` 或 `refutes`）得 0.5；直接證據來自兩條以上不同的 `chain`，再加 0.5。最後依重要性加權平均。沒有核心命題的話，就用全部計分命題算。
- **等級：** 高（≥ 75）、中（50–74）、低（< 50）。
- **可公開：** 完整模式、等級為高、至少一個跨模型席位執行成功。三項都達到才會標「可公開」。
- 所有門檻都是第一版的數字，用 `evals/` 的標準案例校正之後再調整。

### 7.5 不放進可信度的指標

媒體立場、記者署名、報導用詞、操弄手法都不影響可信度，另外放在報告的「報導品質」和「操弄手法」區塊。脈絡類的手法，例如斷章取義、舊圖新用，會反映在命題的判定上，例如判成「誤導」。

## 8. 溯源和背景

- **既有查核：** 事實查核中心、Cofacts、MyGoPen 等機構的結論只當成線索。正方要重驗它們引用的原始資料，報告列出「一致」或「不一致和理由」。
- **媒體：** `fc.py media <網址或名稱>` 查 `media.toml`。
  - 一律列出信任度（Reuters Digital News Report），附年份。
  - 立場只在有學術研究可引用時才列，附年份和出處。沒有的話，顯示「目前沒有可引用的研究」。
- **記者：** 只看有沒有署名，以及這篇報導有沒有被查核機構點名或刊登更正。不評價記者個人。
- **更正和裁罰：** 只記在媒體上，附日期、文號和是否上訴。
- **傳播跡象：** 只描述觀察到的現象，例如大量相同文案、新帳號集中轉傳、可疑網域。只有政府、研究機構或平台的正式報告點名過這個案例，才寫出是誰在操作。
- **一般民眾：** 只記錄帳號的公開資訊，不追查真實身分。

## 9. 操弄手法辨識

`data/tw/tactics.toml` 的每一條包含：編號、台灣口語名稱、分類、層級、定義、看得到的特徵、不能推論的事、一句話辨認方式、DISARM 編號（選填）、對應的脈絡問題（選填），以及至少兩個案例。

**層級：**

| 層級 | 意思 | 報告的寫法 |
|---|---|---|
| `content` | 內容層的手法 | 「這段話用了 X 手法」，並引用原文是哪一段 |
| `spread` | 傳播跡象 | 「觀察到 X 跡象」，附證據 |
| `attribution` | 背後是誰，例如網軍、假旗 | 只能寫「特徵和 X 相符，但無法確認背後是誰」；除非引用正式報告 |

**案例的陣營** 指的是**被攻擊或被抹黑的一方**，不是散布者，因為散布者本身就是歸因。每種手法至少要有兩個案例，涵蓋至少兩個不同的被攻擊方。這條規則由測試強制檢查。

## 10. 法條

- 一定要引用條文原文、條號和版本日期，來源是 lawchat MCP 或法務部的法規資料。
- 白話解釋只能改寫原文。超出條文字面的解讀必須引用判決或大法官解釋，否則寫「此處解讀有爭議，建議諮詢律師」。
- 拿不到條文時，該命題判 `unverified`，並把 `law_text_obtained` 設為 `false`。
- 報告的法條區塊固定標「非法律意見」。

## 11. 錯誤處理

| 狀況 | 處理 |
|---|---|
| 完全無法上網 | 停止，不產生判定 |
| 外部 CLI 逾時或失敗 | 逾時上限 3600 秒（`FC_TIMEOUT` 可調；2026-11-18 實測正方要 9–33 分鐘，拆成 40 個命題的新聞要 33 分鐘；1200 秒時 9 次有 1 次逾時）。逾時不重試，因為用同樣的上限重跑通常還是逾時；程式當掉或結束碼不是 0 才重試 1 次。還是失敗就把該席位標為 `failed`，照信心度規則扣分 |
| 模型輸出格式不對 | 提示正確格式後重試 1 次。還是不對就停止，並回報是哪一步 |
| 付費牆、被擋、被刪 | 改找存檔或轉載，在證據表標 `access_note` |
| 截圖看不清楚 | 標「辨識不清」，不補字 |
| 影片沒有字幕，也沒裝 whisper | 請使用者提供逐字稿。沒有的話，影片命題的 `access_note` 標 `no_transcript` |
| 內容裡夾帶指令 | 一律當成要查的資料 |
| Cofacts 沒有 app-id | 改用網頁搜尋 cofacts.tw，並在報告註明 |
| 社群原始貼文抓不到 | 標「未直接核對原始貼文」，提示使用者可以開啟選裝的瀏覽器自動化，並先警告違反 Meta 服務條款和帳號被鎖的風險 |

## 12. 測試

**CI（`python3 -m unittest`，不呼叫模型）：**
- `score`：固定輸入得到固定輸出；四捨五入；無法判定的條件；信心度每一條扣分；快速模式的上限；可公開的條件。
- `validate`：每種 JSON 的必填欄位、列舉值、範圍。
- `detect`：用假的 CLI 模擬環境，確認同一家模型不算跨模型、本機模型的白名單、探測失敗不算數。
- `run-model`：用假的 CLI 模擬逾時、壞掉的 JSON、重試。
- `finalize`：覆核通過、不通過（標籤維持或改判無法證實）、覆核缺漏、沒有攻擊；溯源和手法攻擊依攻擊對象分流；撤回的手法標記從裁決彙整。
- `render`：檢查每個區塊的內容（結果行、光譜、無法判定時不標分數、爭議點、媒體立場研究、法條聲明、席位隔離程度、撤回的手法標記、辯論後的修正排在所有辯論前段落之後），以及同樣的輸入產出完全相同的報告。
- 資料：`media.toml` 每一筆都有出處網址和年份；`tactics.toml` 每種手法至少兩個案例、涵蓋兩個不同的被攻擊方；`model-tiers.toml` 格式正確。

**發版前手動跑（`evals/`）：**
- 記憶隔離：`fc.py detect --probe` 快篩，加上手動金絲雀測試（見 `evals/README.md`）。
- 誘導式提問：中立、偏藍、偏綠三種問法。
- 對稱性：結構相同、攻擊對象不同的案例。
- prompt injection：內文藏指令。
- 標準案例：答案用第一手資料自己確認，`fc.py eval-compare` 計算準確率。
- 雙平台：Claude Code 和 Codex 各跑一次。
